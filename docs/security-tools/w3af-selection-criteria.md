## w3af を選ぶべき条件

### 1. プラグインアーキテクチャによるカスタマイズが必要

```
✓ Python で独自の脆弱性検査プラグインを書ける
✓ 独自の攻撃パターンを追加したい研究者・セキュリティエンジニア向け
✓ 既存のスキャナが対応していない独自脆弱性を検出したい場合

# 独自プラグインの例
class MyCustomPlugin(AuditPlugin):
    def audit(self, freq, orig_response):
        # 独自の検査ロジックをここに実装
        ...
```

### 2. Linux CLI 環境での完全自動化スクリプト

```
✓ .w3af スクリプトファイルによる無人実行が可能
✓ 画面なし (ヘッドレス) 環境での実行に対応
✓ cron や bash スクリプトからの呼び出しが容易
```

```bash
# .w3af スクリプトで全自動実行
docker run -it --network host \
  -v $(pwd)/scan.w3af:/home/w3af/scan.w3af \
  andresriancho/w3af \
  ./w3af_console -s /home/w3af/scan.w3af
```

### 3. 学術研究・ツール比較目的

```
✓ 3 ツールの比較評価や論文・レポート作成で網羅的に検討したい
✓ プラグイン構造の参考として実装を学びたい
```

### 4. 既存スクリプト資産がある場合の継続利用

```
✓ 過去に .w3af スクリプトを整備済みで移行コストをかけたくない
✓ 特定のスキャンパターンが w3af でのみ再現できる場合
```

## w3af を選ぶべきでない条件

### 1. 実務・本番環境のセキュリティ評価

```
✗ メンテナンス停止により最新脆弱性パターンが未収録
✗ CVE データベースとの連携が古く、新しい攻撃手法を見逃すリスク
✗ False Positive が多く、結果の信頼性が低い
```

### 2. SPA / React アプリのスキャン

```
✗ JavaScript によるルーティングを解析する機能が弱い
✗ React Router や Vue Router で生成されるページを探索できない
✗ AJAX リクエストの追跡精度が低い
```

### 3. JSON ボディへの注入テスト

```
✗ application/json のリクエストボディへのペイロード挿入精度が低い
✗ Go の REST API (JSON ベース) の脆弱性を見落とすリスクが高い
✗ 手動での補完テストが必須になる
```

### 4. Windows / macOS 環境

```
✗ Windows / macOS のネイティブサポートなし
✗ Docker を経由する必要があり、手順が増える
```

### 5. OOB (帯域外) 脆弱性の検出

```
✗ DNS コールバック機能がない
✗ Blind SSRF / OOB SQLi / OOB XXE の検出は不可
```

### 6. CI/CD パイプラインへの安定した統合

```
✗ Docker イメージが古く、最新の OS / ライブラリとの互換性リスク
✗ ZAP の公式 GitHub Actions のような公式統合ツールがない
✗ スキャンが途中でクラッシュするケースが報告されている
```

## 意思決定フローチャート

```
w3af を選ぶ前に以下を確認:

メンテナンスが止まっているツールでも問題ない?
  └── NO → ZAP または Burp Suite を選ぶ

Python で独自プラグインを開発したい?
  └── YES → w3af の検討余地あり (ただし Burp Suite の BApp も検討)

JSON ベースの API が主なターゲット?
  └── YES → ZAP または Burp Suite を選ぶ

SPA (React 等) がターゲット?
  └── YES → ZAP または Burp Suite を選ぶ

URL パラメータ中心のレガシーな Web アプリ?
  └── YES → w3af が動作する可能性あり (ただし ZAP の方が安定)
```

---

## 現実的な推奨方針

```
w3af を単体で使う状況は現在ほとんどない。
以下のように補完的に使うか、完全に代替を選ぶことを推奨:

1. ZAP (主力) + w3af (補完的な検証) の組み合わせ
   → w3af の redos プラグインなど、ZAP にない特定チェックのみ使用

2. w3af から ZAP への移行
   → 既存の .w3af スクリプトを ZAP API スクリプトに書き直す

3. 学習・研究目的での利用
   → プラグインアーキテクチャの参考として Docker で動かす
```

## 推奨導入シナリオ

### シナリオ A: セキュリティ研究・比較評価

```
目的: 複数ツールの検出能力を比較する学術論文を書く
チーム: セキュリティ研究者

→ ZAP / w3af / Burp を同じターゲットに対して実行し結果を比較
→ w3af 独自の redos / dos プラグインの動作を確認する
```

### シナリオ B: 独自脆弱性の検出プラグイン開発

```
目的: 自社独自のビジネスロジック脆弱性を検出するプラグインを作りたい
チーム: Python が書けるエンジニア

→ w3af の plugin/audit/ ディレクトリにカスタムプラグインを追加
   ただし、Burp Suite の BApp (Java) または ZAP スクリプト (Python/Groovy) も同等の柔軟性がある
```

### シナリオ C: レガシー Web アプリのスキャン (URL パラメータ主体)

```
目的: 昔ながらのフォームベースの Web アプリをスキャン
対象: PHP や JSP の伝統的な GET/POST フォーム

→ w3af の audit/sqli, audit/xss プラグインが有効な場合あり
   ただし ZAP の方が安定しているため、まず ZAP で試すべき
```
