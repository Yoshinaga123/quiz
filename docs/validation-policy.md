# バリデーションポリシー

## 目的

本ドキュメントは、クイズアプリにおける入力検証とエラーハンドリングの基準を定める。
対象は `admin-web`、`backend`、`mobile` である。

このポリシーの狙いは次の3点。

- 不正入力や改ざんを `backend` で確実に止める
- `admin-web` と `mobile` では UX 向上のために事前検証を行う
- API 境界をまたぐデータの shape を安定させ、異常系を追跡しやすくする

## 基本原則

- `backend` は常に最終判定を行う。`admin-web` と `mobile` を信頼しない
- 形式検証と意味検証を分ける
- allowlist を基本とし、denylist は補助に留める
- 型、長さ、値域、件数、列挙値、必須性を明示的に検証する
- サニタイズや `trim` は補助であり、安全性の根拠にしない
- 認可や所有者チェックを入力検証で代替しない
- クエリパラメータやソート条件は未検証のまま検索条件や SQL に流さない
- DB 制約は最後の防波堤であり、アプリケーション層の検証を省略する理由にはしない

## 検証の種類

### 形式検証

構文や shape の妥当性を確認する。

- JSON の構造
- 型
- 日付や URL の形式
- 数値範囲
- 最大文字数
- 配列件数
- enum の候補値

### 意味検証

業務ルールや状態遷移の妥当性を確認する。

- そのクイズが更新可能な状態か
- 公開状態の変更条件を満たすか
- 参照先 ID が存在するか
- 重複作成を許すか

## レイヤー別の責務

### `admin-web`

- フォーム送信前に Zod または TypeScript ベースの検証で事前検証する
- API レスポンスは Zod または TypeScript ベースのランタイム検証で shape を確認する
- 表示用メッセージはユーザー向けに限定し、内部エラー詳細はそのまま出さない
- URL クエリを画面状態に使う場合は、復元時にも検証する

補足:

- フォーム検証は UX 改善が目的であり、セキュリティの最終防衛線ではない
- 現在の `admin-web/src/schemas/*.ts` と `admin-web/src/api/*.ts` はこの方針の対象とする

### `backend`

- パスパラメータ、クエリパラメータ、JSON ボディを入口で検証する
- 形式検証はハンドラ境界で行い、業務ルール検証はその先の処理に寄せる
- 未知の JSON フィールドを業務データへそのまま流さない
- 不正入力は早期に `4xx` と機械可読なエラーコードへ正規化する
- 例外系でも、利用者向けメッセージと運用向けログを分ける

補足:

- 現在の `backend` は `main.go` 中心の構成だが、将来ハンドラや DTO に分割しても責務分担は維持する
- 書き込み系エンドポイントでは、可能な限り `json.Decoder.DisallowUnknownFields()` 相当の厳格さを目指す

### `mobile`

- ローカル検証は UX 向上のために行う
- `backend` と異なる独自業務ルールを持ち込まない
- DTO から Entity への変換時に shape の不整合を握りつぶさない
- API エラーは画面表示用文言へ整形し、内部例外をそのまま露出しない

補足:

- `mobile` は最終的に `backend` の API を信頼源とする
- オフライン対応を入れる場合も、サーバー再同期時のバリデーション結果を正とする

## 境界ごとのルール

### 1. API レスポンス

- `admin-web` は `fetch` 後に Zod または TypeScript ベースのランタイム検証で shape を検証する
- `mobile` でも将来的に API DTO の shape を検証する
- `as SomeType` だけで通過させない

### 2. フォーム入力

- 必須、最大長、選択肢、数値範囲をフォーム送信前に検証する
- フィールド単位エラーとフォーム全体エラーを分けて扱う
- 入力中の補助表示と、送信時の最終チェックを混同しない

### 3. URL クエリ

- `page`、`per_page`、`sort`、`status` のような画面状態は明示的に allowlist で扱う
- `page` や `per_page` には上限を設ける
- 不正な値は 400 か安全な既定値へ寄せるかを、API 契約として先に決める

### 4. JSON ボディ

- 書き込み系 API は未知フィールド拒否を基本とする
- JSON の型不一致、余分な値、本文サイズ超過を個別に扱う
- 複雑な payload は DTO から業務データへ明示的に詰め替える

## 正規化ルール

- `trim` は ID、検索語、メールアドレス、URL、短いタイトルのような短文フィールドに適用する
- 改行や空白が意味を持つ本文では、勝手に内部文字列を変形しない
- `trim` 後の空文字を必須違反として扱うかどうかはフィールド単位で決める
- 制御文字除去を行う場合は、どのフィールドに適用するかを明示する

## `null` と欠落の扱い

- `required`、`optional`、`nullable` を区別する
- 「値が未送信」と「明示的に空」は同一視しない
- API 契約上 `null` が意味を持つ場合だけ `null` を使う
- 何でも `null` 許容にする運用は避ける

補足:

- 共通エラーレスポンスのように shape 安定性を優先する場面では、キーを固定して `null` を返す設計は有効
- 一方で更新 API や検索条件では、欠落と `null` を分けた方が自然なことが多い

## エラー契約

API エラーは、少なくとも次の情報を安定して返す。

- `message`: 利用者向けメッセージ
- `code`: 機械可読なエラーコード
- `field`: 特定フィールドに紐づく場合のみ設定

ルール:

- スタックトレースや内部例外文字列をそのまま UI に出さない
- ログには原因追跡に必要な情報を残す
- 一時的失敗と入力ミスを同一ログレベルで扱わない
- 可能なら Request ID をログとレスポンス追跡に使う

## クイズアプリ固有の重点項目

### クイズ編集

- `section`、`title`、`question`、`options`、`correctAnswerIndex`、`source` は明示的に検証する
- `options` は最小件数、空文字、重複可否を決める
- `correctAnswerIndex` は `options` の範囲内でなければならない
- `status` と `pushEnabled` は allowlist または厳密な型で扱う

### 一覧検索

- `page`、`per_page`、`sort`、`status` は enum または範囲制約を持つ
- 未検証の sort 文字列を SQL へ埋め込まない
- 大きすぎる `per_page` は制限する

### ログイン

- 必須項目、空白のみ入力、最小限の形式を `admin-web` 側で検証する
- 認証失敗の詳細を出し分けすぎない

## 実装ガイド

### `admin-web`

- API レスポンススキーマは `src/schemas/` に置く
- フォーム送信用スキーマや型ガードは `src/schemas/` または `src/api/` 近傍に置き、画面側で明示的に検証する
- API エラーのパースと整形は `src/api/` に寄せる

### `backend`

- 文字列の `TrimSpace`、数値変換、enum 判定、ページサイズ上限制御を入口で行う
- JSON デコード後にそのまま永続化せず、必要なら明示的に詰め替える
- DB 制約違反は 500 で握りつぶさず、期待される入力違反なら 4xx に寄せる

### `mobile`

- Presentation 層では入力補助のための軽い検証に留める
- `data` 層で DTO 変換失敗を検知できる構造にする
- `domain` 層にはサーバーとズレる独自ルールを増やしすぎない

## チェックリスト

新しい入力項目や API を追加する時は、次を確認する。

1. required / optional / nullable が定義されているか
2. 型、長さ、値域、件数、enum が定義されているか
3. 形式検証と意味検証の責務が分かれているか
4. `admin-web` / `mobile` の事前検証と `backend` の最終検証が両方あるか
5. 不正なクエリや JSON shape を拒否できるか
6. エラーコードとユーザー向けメッセージが決まっているか
7. ログに原因追跡情報を残せるか
